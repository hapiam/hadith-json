# amrayn <-> fawaz hadith-counting relationship, verified per citation

Generated by `tool/build_numbering_relationship_map.dart` (per-citation
content-matched correspondence) plus `tool/investigate_fawaz_internal_duplication.dart`
(explains part of the "amrayn never matches this fawaz row" cases below).
Different sources report different "total hadith count" for the same book
-- this file records the ACTUAL, per-citation-verified reason why, not an
assumption. Matches are by Arabic text content (`arabic_match.dart`), never
by citation number, so this is checking a real correspondence, not circular
reasoning from the numbers themselves.

**Correction (post matcher fix):** every number below was regenerated after
fixing a real bug in `arabic_match.dart`'s anchor pass -- it took "first
occurrence wins" on a 60-char prefix collision, but many hadiths share an
identical isnad opening 60+ characters long (e.g. Malik -> Hisham ibn
Urwah -> his father -> A'isha, reused across dozens of unrelated reports),
so a meaningful number of citations were silently attached to the wrong
fawaz row. This inflated how much of the "amrayn never matches this fawaz
row" gap looked explainable by fawaz's own internal duplication (the
earlier run of this file claimed 67.6%-97.7% per book; the true figure,
below, is 11.9%-54.4%). See `sources/amrayn.com/BOOK_MISMATCH_QUALITY.md`
for the concrete before/after verification of the fix.

## The two things that make "total hadith count" differ between sources

1. **Amrayn splits some fawaz-numbered narrations into multiple lettered
   citations** (e.g. `8a`/`8b`) where fawaz keeps them under one number.
   Verified directly per book below ("N amrayn citations -> 1 fawaz row"
   tables).
2. **Fawaz's own file repeats the same hadith text under more than one row
   number** -- most prominently Bukhari's well-known convention of citing
   the same narration again under a different chapter for isnad-analysis
   purposes. Where this happens, amrayn's single citation for that content
   already "uses up" its match against ONE of the fawaz duplicates, leaving
   the other fawaz occurrence(s) showing as "amrayn never matches this row"
   even though the underlying hadith IS represented once. Verified per book
   in the **Internal-duplication check** table below -- explains only a
   modest fraction (11.9%-54.4%) of the unmatched-row count, smaller than
   this file previously claimed (see correction note above). Most of the
   "fawaz rows amrayn never matches" gap is genuinely unexplained by this
   effect and remains open -- either amrayn content amrayn genuinely lacks
   from that fawaz row, or fawaz content simply not represented anywhere in
   amrayn's own citation set.

**Malik is the clearest outlier**: internal duplication explains only
20.8% of its gap, and its own book/chapter relationship to fawaz is
structurally different from the other 6, not just the same two effects at
a different scale. `tool/investigate_malik_book_join.dart` found a real
join key `BOOK_CHAPTER_CROSSCHECK.md` never checked -- fawaz's own RAW
`reference.book` field (separate from the canonical `chapterId` rebuild
that file was actually about) -- which agrees with amrayn's
`malikChapterNum` 96.0% of the time (post matcher-fix; was 86.0% before).
But the residual disagreement isn't narrow boundary drift like the other 6
books: the gap between the two book numbers GROWS as the book progresses
(single digits early, into the 40s-50s by the end, even though both
sources independently cap at 61 total books). See
`sources/amrayn.com/MALIK_BOOK_JOIN.md` for the full breakdown -- this
looks like a genuine manuscript-recension difference (Muwatta Malik has
multiple real historical transmission lines with different chapter
groupings), not a data defect, but confirming exactly which recension each
source follows needs a third source or direct scholarly reference, not
further automated matching between just these two.

## Internal-duplication check (explains part of "fawaz rows amrayn never matches")

For every fawaz row amrayn never matches, checks whether a near-identical
text exists elsewhere in fawaz's own file, and whether amrayn already
matched THAT occurrence -- if so, the row isn't a real gap, just a
fawaz-internal repeat. Caveat: this check only looks for an EXACT 60-char-
prefix match within fawaz's own file (cruder than the full fuzzy matcher
used for the amrayn<->fawaz comparison itself), so "no duplicate found"
below is likely still a slight overstatement of genuinely-open cases.
